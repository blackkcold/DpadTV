# 动态加载 + 剩余缺陷修复 · `20261025f`（1.2.1）

> 本轮：①取数改成「用户动作驱动 + 门控」；②把上一轮遗留的 P1/P2/R 项做完；③在**模拟器**上跑完整走查；④打包并覆盖安装到电视（未启动、未实机测试）。

## 1 · 取数策略：启动 0 请求，滚动才联网

| 规则 | 实现 |
|---|---|
| 首页不预取 | `fetch(ref)` 默认 `allowNetwork=false`：首页整页只吃本地索引；本地没有 → 显示「点这里联网取」，用户按了才发请求 |
| 滚动才分页 | `loadMore()` 只在滑到底触发；`fetchQuery` 本地凑够半页（≥6）就不联网 |
| 最小间隔 | 3s + 0~0.9s 抖动（固定节拍最容易被识别成脚本） |
| 配额 | 10 分钟最多 20 次；超了直接返回「稍后再试」，不撞豆瓣 |
| 风控退避 | 403/418 或「检测到有异常请求」→ 10m → 20m → 40m → 80m（上限 2h）；`Retry-After` 优先 |
| 失败分类 | IOException → OFFLINE（不惩罚），5xx → 60s 冷却，业务空 → UPSTREAM |
| 失败不串味 | 每次调用带自己的 `Outcome`，并发时文案不会张冠李戴（R8） |

**模拟器实测**：`adb logcat -c` 后冷启动，8 秒内 `DpadTVDouban direct OK` 计数 = **0**；首页 3 行 + 片单行全部由本地索引渲染（电影 18 部 / 剧集 17 部 / 综艺 24 部）。

## 2 · 索引构建：不再一次性全量

- 新增 `--max-requests`（默认 40）全局预算 + 3~4s 随机间隔；命中风控立即熔断本轮。
- 新增 `--lists`：把 **TOP250（50 条，保持榜单顺序）** 与奥斯卡豆列预生成进索引 → 运行时策展榜也是 0 请求，且不会和「9 分+」整行重复（上一轮 P1-8 的根因）。
- 新增 `--repair-year`（离线反推）/ `--enrich-years`（按需补「类型×年份」组合，可 `--only` 单类补量）。
- 索引现状：**1661 条 / 31 标签 / year 覆盖 508（30.6%）/ gzip 52KB**；Top250 50 条、奥斯卡 5 条。

# 追加 · 方案 L（主键方案复核 → 改用命中排序）

## 复核结论：**不改主键**（此前的判断需要更正）

先把「同名不同片」的现场抓下来：直接打 `/api/search?wd=控方证人`，**22 条命中**：

```
360资源  | 控方证人 | 2025 | 全75集（合全集） | 爽文短剧   ← 服务端第一条
360资源  | 控方证人 | 1957 | 正片            | 悬疑片
电影天堂 | 控方证人 | 1957 | HD中字          | 剧情片
…
量子资源 | 控方证人[电影解说] | 1957 | 已完结 | 电影解说
如意资源 | 控方证人短剧      | 2025 | 已完结 | 短剧
```

结论：**不是合并串味，是「取第一条」**。`resultGroups` 按片名分组后取 `items.first()`，
而服务端顺序是**源的顺序**，不是匹配度。所以改主键（source+id）对症状无效 ——
它解决的是「同名两部片在片单里共存」，那是另一个问题。

# 追加 · 方案 M（片单主键迁移 v3→v4）

## 一、影响核查（动手前）

| 调用点 | 旧签名 | 影响 | 处理 |
|---|---|---|---|
| `PosterActions.show/stateLine/badgeFor` | `stateOf(title)` / `remove(title)` | 3 处 | 改为接收 `MovieItem`，走新身份 |
| `LibraryStore.toggle` | `toggle(item,state)` | 内部 | 内部改 `stateOf(item, refKey)` |
| `MainActivity` 详情「加入片单」 | `put(item, FAV)` | 无源身份 | 传入 `LibKey.ref(sourceUrl, vodId)` |
| `MainActivity.playFromList` | `stateOf(title)` | 播放写「在看」 | 增加 `refKey` 参数，按源身份判定 |
| `LibraryScreen` | `store.list()` / `LibEntry` | 结构体变了 | `LibEntry` 增 `id`/`refKey`，`toItem()` 不变 |
| `Recommend` + 测试 | `LibEntry(...)` 构造 | 编译期 | 补 `id = LibKey.legacyTitleKey(title)` |
| 历史 / 播放进度 | `Prefs.HistoryEntry` / `progressOf(url)` | **不受影响** | 进度本来就按集 URL 存，天然唯一 |

## 二、迁移设计

- 身份优先级：`d:<豆瓣id>` → `r:<源URL>|<vodId>` → `t:<归一化片名>`。
- DB v3 → v4：SQLite 不能改主键，**重建表**；老行折算成 `t:` 并保留 state/cover/rating/source。
- **就地认领**：升级后第一次写入，`findId()` 按 douban_id → ref_key → `t:` → `title` 依次找，
  命中老行就把新身份补上，不产生重复条目。
- 同一部片从两个源加：豆瓣 id 相同 → 归并成一行；同名不同片 → 豆瓣 id 不同 → 两行共存。
