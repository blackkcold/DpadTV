# 审计：筛选慢、无高亮、以及「要不要把榜单内置进 App」

> 范围：`BrowseScreen`（查看更多/筛选页）、`CollectionRepo`（抓取/缓存/侧车）、`sidecar/`（Docker 侧车）、`Shelves`（榜单注册表）。
> 方法：只读复核源码 + 逐条追时序。**本轮不改代码**，只出结论与方案。
> 基线：`feature/collections@e6165ce`（含本轮 Aerial 改造）。

---

## 0. 一句话结论

三个症状其实是**两个独立根因**：

| 症状 | 根因 | 性质 |
|---|---|---|
| 点「日本」没有高亮 | `filterRow()` 只在 `build()` 时渲染一次，点击后只重建 chip 不重建筛选行 → 选中态**永远是初始值** | **纯 UI bug**，10 行能修 |
| 点完空白、像卡住 | `reload()` 先 `items.clear()` 把网格清空，只在一行小字上写「加载中」，没有骨架/遮罩/进度 | 交互缺陷 |
| 加载慢（2.5s 起、常常更久） | 每次切标签 = **一次豆瓣搜索**；直连路径全局串行 + 2.5s 节流，命中风控封 60 分钟 | **架构问题** |

而「要不要内置进 App」的答案是：**该内置的不是客户端，是数据**。
豆瓣榜单是**周级变化的公共元数据**，被我们当成了实时搜索在用 —— 这是所有慢和限流的源头。

## 1. 证据（每条都能指到行）

### 1.1 高亮不更新

```kotlin
// BrowseScreen.kt:205  filterRow() —— 一次性建好，on 是建行那一刻的快照
values.forEach { v ->
    val on = when (name) { "年份" -> ...; "地区" -> (region ?: "全部") == v; ... }
    row.addView(TextView(host).apply {
        setTextColor(if (on) accent else muted)      // 之后再也不重算
        setOnClickListener { onPick(v) }
    })
}

// BrowseScreen.kt:116  点击只做三件事：改字段 → 重建 chip → 发请求
col.addView(filterRow("地区", listOf("全部","华语","欧美","韩国","日本")) { v ->
    region = if (v == "全部") null else v; activeChip = null; activeRef = null; renderChips(); reload()
})
```

`renderChips()`（:156）只重建 `chipsRow`，**没有任何一行调用 filterRow**。所以：

- 颜色不变（仍是初始的「全部」高亮）；
- 焦点还被 `renderChips()` 的 `removeAllViews()` 一起扔掉 —— 遥控器上表现为「点一下，框没了」。

### 1.2 空白 + 无进度

```kotlin
// BrowseScreen.kt:276
private fun reload() {
    items.clear()                 // 立刻清空 → 网格变白
    done = false
    adapter.notifyDataSetChanged()
    status.text = "  · 加载中"     // 只有这一行 12.5sp 的小字
    loadMore()
}
```

侧车不在线时，一次请求 = 队列等待 + 2.5s 节流 + 8s 连接超时，最长可达十几秒的空白屏。

### 1.3 慢的真实来源

```kotlin
// CollectionRepo.kt:118  request() —— 全局一把 Mutex
private suspend fun request(url: String): String? = gate.withLock {
    if (douban != null && sidecar != null) { /* 侧车命中：毫秒级 */ }
    val gap = 2500 - (System.currentTimeMillis() - lastRequestAt)
    if (gap > 0) delay(gap)                 // 直连：每次至少隔 2.5s
    ...
}

// CollectionRepo.kt:40  侧车地址是推导出来的，不是配置项
val sidecar = "http://${URI(Prefs(ctx).serverUrl).host}:8898"
```

| 事实 | 影响 |
|---|---|
| 缓存键 = `md5(url)`（:101） | **每个筛选组合都是新 URL** → 第一次点「日本」必然打一次网络；组合越多命中率越低 |
| 全局串行 + 2.5s 节流 | 分页滚动一页 2.5s 起；切两个筛选 = 5s+ |
| 侧车地址硬编码 `:8898` | 换服务器/改端口就静默退回直连（更慢、更容易被封） |
| 命中风控后 `blockedUntil = +60min` | 一旦中招，整页功能停摆一小时，且**没有可见的重试入口** |
| 侧车 `offline-miss` 已与限流分开判态（:145） | ✅ 这块上一轮修对了，不要再退回去 |

## 2. 从第一性原理重问一遍

**用户点「日本」时到底要什么？** 要的是「一屏日本片」。

「发起一次豆瓣搜索」是**实现手段**，不是需求。把手段当需求，就必然：
每次交互都付一次网络往返、一次节流、一次风控风险。

**榜单数据是什么？** 公开的、周级变化的、纯元数据（标题/评分/年份/封面 URL/来源）。
它不像播放地址那样每次都可能变，也不像用户片单那样私有 —— 它是**可以预生成、可以离线、可以随包发布**的东西。

**唯一的重资产是图片**，而图片已经走 LibreTV 的 `/api/proxy`，跟豆瓣限流无关。

所以问题的正确切分是：

```
内容元数据  ← 应当内置（静态索引，随 APK 发布）
封面图      ← 继续走服务端代理（已有）
播放地址    ← 继续实时聚合搜索（本来就是这样）
```

**结论：不需要「把服务端内置」，需要把「榜单索引」内置。** 侧车从「运行期依赖」降级为「构建期工具」。

## 3. 方案对比（按用户能感知的差异排，资源开销放最后）

| 维度 | A. 现状 + 修 UI | **B. 内置索引（推荐）** | C. 内置 + 后台静默刷新 |
|---|---|---|---|
| 切筛选标签 | 1–3s（侧车）／2.5s×n（直连） | **0ms，本地过滤** | 0ms |
| 首屏 | 需要网络 | **0 请求** | 0 |
| 无网/豆瓣风控时 | 只能用缓存过的组合 | **全都能用** | 全部 |
| 分页滚动 | 每页一次请求 | **本地分页，0 请求** | 本地优先 |
| 榜单更新 | 实时 | 每周跑一次生成脚本 | 后台增量，用户无感 |
| 需要 Docker | 是（侧车） | **否**（构建期跑一次） | 否（可选） |
| APK 体积 | 6.3 MB | **+0.15 ~ 0.3 MB** | 同 B |
| 实现成本 | 0.5 天 | 1.5 天 | +0.5 天 |

**推荐 B**：它把「慢」和「限流」一起消掉，且删掉一个常驻服务。
C 的增量刷新收益主要是榜单新鲜度，等 B 稳定后再加。

## 4. 内置索引怎么做

### 4.1 数据规模（算给你看）

- 单标签取 100 条：`j/new_search_subjects?tags=<标签>&sort=T&page_limit=100`
- 标签池取 40 个（地区 5 + 类型 8 + 年份 4 + 剧集/综艺 若干 + TOP250/豆列）
- 去重后约 **3000–4500 条**
- 每条 JSON：`title/cover/rate/year/badge` ≈ 150–180 B → **≈ 700 KB 原始**
- gzip 后 **≈ 160–200 KB**（中文 JSON 压缩比通常 4:1）

对比：现在 APK 6.3 MB，加 **2.5%**。而一次冷启动首页现在要打 4 行 × 3–4 个榜 = 十几请求。

### 4.2 结构

```
app/src/main/assets/index/
  tags.json.gz      # { "日本": [id...], "悬疑": [...], ... }  倒排索引
  items.json.gz     # { "douban-1234567": {t,r,y,c,b} }         条目表
  meta.json         # 生成时间、来源、条数、schema 版本
```

倒排索引是关键：**筛选 = 多个标签集合求交**，客户端毫秒级；不需要为 5×8×4 种组合各存一份。

### 4.3 运行时

```kotlin
object LocalIndex {                       // 纯 JVM，可单测
    fun load(ctx: Context): Index          // 首次访问解压到内存（≈10ms）
    fun query(tags: List<String>, year: String?, sort: Sort, start: Int, size: Int): List<MovieItem>
}
```

`BrowseScreen.reload()` 改成：**先本地出结果（同步、0 延迟）**，状态栏写「本地索引 · 2026-10-20」；
只有「本地不足 6 条」或用户点「联网刷新」时才走 `CollectionRepo`。

### 4.4 生成脚本（构建期，不是运行期）

`tools/build-index.mjs`：

1. 读 `Shelves.kt` 里的标签池（或一份 `tools/tags.json`）
2. 走 sidecar 的 `/douban?path=...` 批量抓（复用它的串行+缓存，抓完就退出）
3. 归一化标题、去重、截断、按 (评分, 热度) 排序
4. 写 `assets/index/*.json.gz`
5. 输出 `meta.json`（条数、时间），CI 里加一条「索引超过 30 天就提醒」

> 这一步是**在笔记本上跑**的，不需要路由器上常驻任何容器。

## 6. 风险与边界

| 风险 | 说明 | 对策 |
|---|---|---|
| 索引有覆盖上限 | 内置 3000–4000 条，冷门片搜不到 | 「聚合搜索」链路不变，冷门片靠搜索；索引只负责"逛" |
| 数据会过期 | 榜单周级变化 | `meta.json` 带日期，UI 标「索引 2026-10-20」，30 天提醒重建 |
| 体积 | +160–200 KB | 可接受；后续可把索引拆成"必装 10 个标签 + 可选下载" |
| 合规 | 只存公开榜单的**标题/评分/年份/封面 URL**，不存任何视频地址 | 与现状一致，README 免责声明已覆盖 |
| 侧车删掉后首页变慢？ | 首页 4 行 × 3–4 榜也要抓豆瓣 | P1 之后首页同样吃本地索引，一并解决 |
| 生成脚本需要网络 | 跑在笔记本，豆瓣限流时抓不全 | 复用侧车的缓存目录，分批跑；增量只补缺失标签 |

| sidecar | **已移除**：App 内 `:8898` 与整段侧车协议删掉、`sidecar/` 目录删除、路由器容器 `douban-cache` 已 stop + rm |
| APK | `dist/DpadTV-Pro-1.2.0-20261025d-index-debug.apk`（6.37 MB，索引 +45 KB） |

### 8.1 两个边界（不是 bug）

1. **豆瓣单标签上限 ≈180–200 条**：`start=160` 之后基本返回空（`欧美` 只有 19 条）。所以「日本∩电影」只有 9 条 —— 交集天然比单标签薄。低于 6 条时 App 自动回落联网，状态栏会写「这个组合本地没有（按 OK 联网取）」。
2. **封面仍需网络**：索引只存元数据，图走 LibreTV `/api/proxy`。首屏 hero 图可能有 1–2s 才出现，已加「幕布底色」兜底，不会先给一块黑洞。

### 8.2 为什么最终确认「不需要 docker」

决定性证据来自这次抓取本身：**同一个 URL，路由器直连返回 429（IP 被限），笔记本直连返回 200**。
也就是说侧车解决的问题是「换一个 IP 去抓」+「共享缓存」，而这两件事都可以在**构建期**做掉：

- 抓取：`tools/build_index.py` 在能通网的机器上跑，一次生成，随包发布；
- 缓存：索引本身就是缓存，且比 7 天 TTL 的 HTTP 缓存更可控（带 `built` 日期）；
- 运行期：App 完全不访问豆瓣，只剩「封面图走自家服务端」。

于是路由器上那台常驻容器从「必需品」变成了「多余跳板」，已停掉。
以后要更新榜单：`python3 tools/build_index.py --direct --pages 9 --gap 7` → 提交 assets → 发版。
