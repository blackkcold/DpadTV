03

第一性原理：用户要的是「一屏日本片」

不是「发起一次豆瓣搜索」
把问题拆对现在的做法应该怎样
内容元数据
标题 / 评分 / 年份 / 封面 URL		实时请求豆瓣预生成静态索引随包发布。它是周级变化的公共数据，不是实时接口。
封面图走 LibreTV /api/proxy不变。图片才是重资产，跟豆瓣限流无关。
播放地址点海报 → 聚合搜索不变。这条链路本来就该实时。

把「榜单」当实时搜索用，是所有慢和限流的源头。该内置的是索引，不是客户端；侧车从「运行期依赖」降级成「构建期工具」。

04

内置索引的账

算出来，不是估出来
项数
标签池 × 每标签条数40 × 100（地区 5 / 类型 8 / 年份 4 / 剧集综艺 / TOP250 豆列）
去重后条目3000–4500
每条 JSON（title/cover/rate/year/badge）≈ 150–180 B → 原始 ≈ 700 KB
gzip 后≈ 160–200 KB（APK 从 6.3 MB → +2.5%）
结构tags.json.gz 倒排 + items.json.gz 条目表 + meta.json（日期/版本）
筛选 = ？多个标签集合求交，毫秒级；不需要为 5×8×4 种组合各存一份
