# M3 记录：片单四态 + 豆瓣缓存 sidecar

## 一、片单（收藏 / 想看 / 在看 / 看过 / 弃剧）

| 决策 | 原因 |
|---|---|
| 四态 + 弃剧，**互斥**而非布尔星标 | 电视上的心理模型是「放进哪个抽屉」，不是「打没打星」 |
| 主键用 **title** | 这个 App 的播放链路本来就是「按片名聚合搜索」，title 才是真 ID；豆瓣 ID 只用来取海报 |
| 长按 OK 弹菜单 | 长按是遥控器上仅次于 OK 的肌肉记忆，比「进详情页再找按钮」快，也不占首屏 |
| 同态再选 = 取消 | 遥控器上「反悔」必须一键，不能让用户去别的页面删除 |
| 首页第一行 = 我的片单 | 自己攒的片单比任何公共榜都更该占这个位置；**有内容才出现**，空的时候不浪费一行 |
| 首次收藏即时长出该行 | 只做「插入」不做「重建」：重建会扔焦点，电视上焦点乱跳比多等一次更难受 |

存储：`SQLiteOpenHelper`（`dpadtv_library.db`），**不引 Room**——项目零注解处理，加 KSP 的构建风险大于收益。

## 二、豆瓣缓存 sidecar（`sidecar/`）

客户端直连豆瓣的死结：冷启动 10+ 个请求 → 家宽 IP 必然被风控 → 首页一半变「暂时取不到」。

放到路由器上（`douban-cache`，`node:20-alpine`，host 网络，**:8898**，缓存落 `/overlay/upper/opt/docker/Configs/douban-cache/cache`）。

### v1 的 bug：假限流

v1 在 `ALLOW_UPSTREAM=0`（验收期只读模式）时，把没有缓存的请求伪装成豆瓣风控响应返回：

```json
{"msg": "offline mode: no upstream access", "r": 1}
```

客户端靠 `body.contains("\"r\":1")` 猜状态 → 判定为「豆瓣限流」→ 退避 10 分钟 → 倒计时每次加载都重置 →
UI **永远**显示「豆瓣限流，N 分钟后自动恢复」，而侧车从没打过一次豆瓣。

### v2 的规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | **读 `X-Cache` 头判态**，body 不参与 | 猜 body 会把「配置态」误判成「限流」，v1 就栽在这 |
| 2 | 响应码语义化：200 有内容 / 429 真限流 / 503 配置或上游错误 | 三件事必须能区分，否则 UI 只能撒谎 |
| 3 | `ALLOW_UPSTREAM=0` 返回 `offline_miss`，**不设退避** | 这不是豆瓣的错，退避只会把问题锁死 |
| 4 | 命中一次限流即熔断 30 分钟 | 实测连续 16 个请求（6s 间隔）必被限流，重试是负收益 |
| 5 | **分批预热**：每 30 分钟一批、每批 ≤10 个 | 一天内补齐 34 个目标，永远不连续撞墙 |
| 6 | TTL 7 天 | 榜单按天变化；缓存 3 天的数据没人抱怨，限流会 |
| 7 | 豆列（`www.douban.com`）一并代理 | 消除最后一条裸奔的直连路径 |
| 8 | `stale` 兜底 | 上游挂/限流时返回旧数据，绝不空手 |

客户端（`CollectionRepo`）：先打侧车；侧车不可达才直连一次，失败后**退避 60 分钟**（v1 是 10 分钟且每次重试）。
只有真 `rate-limited` 才提示豆瓣；`offline-miss` 文案是「缓存还没准备好」，不再甩锅给豆瓣。

实测（v2，2026-10-25）：
- 冒烟 8 个目标 → `ok=8 failed=0`，12s；
- 全量 34 个 → 跑到第 16 个触发真限流，熔断自动中止；
- 首页三行所需 8 条 URL 中 7 条 `X-Cache: hit`，仅「纪录片」落在熔断窗口内 → 由定时批次补上。
- 结论：**首页核心榜单全部本地命中，0 次上游请求**；长尾筛选组合按批补齐。

## 三、已知取舍

- 单次连续抓取 16 个以上会被限流，因此预热必须分批；「纪录片」这类排在矩阵尾部的最坏要等 1–2 小时才补上。
- 侧车不可达（公司网）时客户端会直连一次，失败后退避 60 分钟，期间只吃本地缓存。
- 目前不自动标记「看过」——需要接播放回调，留给 M4。
