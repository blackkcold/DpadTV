# M3 记录：片单四态 + 豆瓣缓存 sidecar

## 一、片单（收藏 / 想看 / 在看 / 看过 / 弃剧）

| 决策 | 原因 |
|---|---|
| 四态 + 弃剧，**互斥**而非布尔星标 | 电视上的心理模型是「放进哪个抽屉」，不是「打没打星」 |
| 主键用 **title** | 这个 App 的播放链路本来就是「按片名聚合搜索」，title 才是真 ID；豆瓣 ID 只用来取海报 |
| 长按 OK 弹菜单 | 长按是遥控器上仅次于 OK 的肌肉记忆，比「进详情页再找按钮」快，也不占首屏 |
| 同态再选 = 取消 | 遥控器上「反悔」必须一键，不能让用户去别的页面删除 |
| 首页第一行 = 我的片单 | 自己攒的片单比任何公共榜都更该占这个位置；**有内容才出现**，空的时候不浪费一行 |
| 首次收藏即时长出该行 | 只做「插入」不做「重建」：重建会扔焦点，电视上焦点乱跳比多等一次更难受 |

存储：`SQLiteOpenHelper`（`dpadtv_library.db`），**不引 Room**——项目零注解处理，加 KSP 的构建风险大于收益。

## 二、豆瓣缓存 sidecar（`sidecar/`）

客户端直连豆瓣的死结：冷启动 10+ 个请求 → 家宽 IP 必然被风控 → 首页一半变「暂时取不到」。

放到路由器上（`douban-cache`，`node:20-alpine`，host 网络，**:8898**，缓存落 `/overlay/upper/opt/docker/Configs/douban-cache/cache`）：

1. **共享缓存**：全屋设备吃同一份 24h 缓存，电视重装/手机/新客户端都不再各自打一遍；
2. **单飞**：同一个 URL 并发只打一次上游；
3. **全局串行 2.5s**：侧车是唯一的出口，永远不会自己把自己封掉；
4. **陈旧兜底**：上游挂/限流时返回过期缓存（`X-Cache: stale`），绝不空手；
5. **限流重试**：识别到 `检测到有异常请求` 隔 6s 再试一次。

客户端：`sidecar` 地址由服务器地址推导（`http://<host>:8899` → `http://<host>:8898`），
先打侧车，失败才回退直连；**直连的 10 分钟退避不影响侧车**（否则一次直连失败会把整条路堵死）。

实测：冷启动 7 个请求全部 `X-Cache: hit`，**300ms 内全部返回**（此前直连要 18 秒且大概率触发风控）。

## 三、已知取舍

- 侧车没有缓存且上游正在限流时，这一行仍会「暂时取不到」；等 IP 解封后下一次打开会补上并缓存 24h。
- 侧车只代理 `movie.douban.com`；豆列（`www.douban.com/doulist/...`）仍走直连。
- 目前不自动标记「看过」——需要接播放回调，留给 M4。
